# AI運用ナレッジ(実データ集約)

TRust-BO開発(2026-06〜07)で実運用したマルチエージェント体制の記録と分析。
**運用規約の一次情報源は `CLAUDE.md`「エージェント運用規約」節**であり、本書は
その根拠となる実データ・役割設計の理由・妥当性評価を保持する(規約の重複記載はしない)。

最終更新: 2026-07-16(3Dフロントウィング実用検証ジョブ完了時点)

---

## 1. 体制の全体像

```
ユーザー(方針決定・承認ゲート)
  └─ Claude Code(指揮官) ← 本体。計画立案・コア実装・統合判断・A/B裁定・最終報告
       ├─ サブエージェント(Claude系)  … 調査・探索の並列化
       │    ├─ Explore: リポジトリ内の読み取り調査(陳腐化監査、実装箇所特定)
       │    └─ general-purpose: Web文献調査(役割を明示した並列リサーチ)
       └─ Codex CLI(OpenAI系)        … 独立実装・独立レビュー(系統の異なる知能)
            ├─ gpt-5.6-terra (-c model_reasoning_effort="high"): 定型実装
            ├─ gpt-5.6-sol (デフォルトeffort): 数学・数値の精密レビュー、候補吟味
            └─ gpt-5.6-sol (-c model_reasoning_effort="xhigh"、通称 sol ultra):
               最終リリース前監査・最難関タスク
```

役割分担の設計理由:
- **指揮官集中**: ステートレスRustコア+決定性という本プロジェクトの不変条件は、
  文脈を全部持つ1体が守るのが最も安全。コアアルゴリズム(cem.rs等)の変更と
  採否判定は委譲しない
- **異系統によるダブルチェック**: Claude実装をClaude がレビューするより、
  系統の異なるCodex(GPT)に監査させる方が盲点が直交する。
  「実装 ⇔ 独立レビュー ⇔ 実測A/B」の三重化が機能した実績多数(§3)
- **調査は並列サブエージェント**: 文献調査・大規模コード監査は読み取り専用で
  失敗しても壊れないため、並列化の利得(壁時計短縮)が最大化する
- **トークン経済**: Claude本体のコンテキストを実装詳細で消費せず、
  委譲先の要約だけを受け取る(ユーザー明示要求)

## 3. 三重チェックの検出実績(なぜこの体制なのかの根拠)

| 検出者 | 検出物 | 見逃した場合の損害 |
|---|---|---|
| sol レビュー | 制約付きTSの符号誤り、Box-Muller偏り (06-07月) | 制約付き最適化の品質劣化が本番流出 |
| ビット一致検証 | terraのwarm path破壊 (06-07月) | 「warm開始後にbestが改善しない」障害が静かに流出 |
| sol レビュー | Hvarfner事前の論文パラメータ不一致 (07-11) | 「論文準拠」と偽る実装でA/B判定 |
| Claude検収 | terraのSMOKE CSV汚染 (07-12) | 本走resumeが smoke結果をスキップ扱い→データ欠損 |
| **sol ultra監査** | **RAASP σ人工収縮 (07-12)** | 欠陥実装でRAASPを棄却→手法か実装か区別不能→将来の再検証コスト |
| Claude統合 | R3の棄却済み案再提案 (07-12) | 棄却済みのPhase2事前を再実装する無駄 |
| sol xhigh監査(2回目) | joint batch選択の閾値方式が未根治 (07-15) | 1回目の修正だけで採用していれば同型バグを含んだままA/Bへ投入していた |
| sol xhigh監査(1〜3回目) | 3Dパイプラインの`su2_cauchy`誤検知(SIGTERM+文字列マッチ)、Cauchy平均範囲不一致、fingerprint網羅不足 (07-16) | **Claude自身が実装した収束判定の修正それ自体に新しいバグが混入**していた。監査なしなら未収束データを収束扱いで250評価本走に投入していた |

どの層も他の層が見逃したものを拾っており、**3層のどれを外しても実害が出ていた**。
特に07-15/07-16の2件は、「修正した本人が次の欠陥を見逃す」パターンが繰り返し
発生することを示しており、**監査は1回で終わらせず、指摘が尽きるまでループを回す**
という運用規約(CLAUDE.md参照)の直接的な根拠になっている。

## 4. 失敗と無駄の記録(数値つき)

| 事象 | 損失 | 原因 | 対策(規約化済み) |
|---|---|---|---|
| terraハング (07-11) | 壁時計1.5h | timeout未設定+早期確認なし | `timeout 1500`必須。5分時点の出力生存確認は未仕組み化(改善余地) |
| raasp75の128ラン破棄 (07-12) | ~15分の計算+再実行 | **監査前にA/Bへ投入**した順序ミス | 新実装はA/B投入前に監査を通す |
| sol出力のtail切詰め×2 (07-12) | 再監査48,524トークン+10分 | `\| tail -N`で前半喪失 | Codex出力は全量をファイルへリダイレクトし Read する |
| R3への棄却リスト渡し忘れ (07-12) | R3出力の~1/5 | プロンプト指示の不均一 | 調査エージェントには棄却済みリストを必ず貼る |

## 5. 損益の目安(いつ委譲すべきか)

実データから得た経験則:

- **委譲が得**: (a) Web文献調査(本体でやるとコンテキストを大量消費) (b) 参照実装を
  指定できる定型ハーネス (c) 数学・数値の独立監査(異系統の価値) (d) 10ファイル級の
  横断読み取り監査
- **自前が得**: (a) コアアルゴリズム変更(不変条件の保持は文脈を持つ者の仕事)
  (b) 小さなmd編集・数行のバグ修正(委譲仕様を書く方が高い) (c) 採否判定・統合判断
- **検収コストは固定費**: terra委譲は「委譲コスト+検収(差分レビュー+SMOKE ~10分)」で
  見積もる。500行級ハーネスなら得、50行未満なら自前が速い
- **監査の階層**: 通常レビュー=sol、最終実装・公開物=sol ultra(xhigh)。
  実績上、xhighのみが数式レベルの欠陥(σ収縮)に到達した

## 6. 再現用プレイブック(良かった運用の手順書)

将来のセッションが同じ品質の運用を再現するための具体手順。§2-5の実データが根拠。

### 6.1 委譲の型: 「誰に・何を・どこまで・後処理」

#### terra への実装委譲(ハーネス・ラッパー類)

- **何を**: ベンチハーネス、Python層ラッパー等の定型コード(500行級まで)
- **どこまで**: 肉付けのみ。**設計はプロンプト側で固定する** — クラス構造・引数名・
  CSV列・アーム構成・SMOKE仕様・参照実装のファイルパスまで明記し、terraに設計裁量を
  残さない(裁量が入った箇所がバグになった実例: SMOKE時CSV名)
- **プロンプト必須要素**: (1)参照実装の具体パス (2)既存慣習の名指し(bench_resume/
  SMOKE/CSV追記) (3)「実行はしない」(4)出力形式(変更ファイル一覧をN行で)
- **起動形**: `timeout 1500 codex exec -s workspace-write -m gpt-5.6-terra
  -c model_reasoning_effort="high" '...'`(timeoutなしで起動しない)
- **やらせた後の処理(検収パイプライン、省略禁止)**:
  1. `git status --short` で変更ファイルが依頼範囲内か確認(範囲外変更は即戻す)
  2. 納品物の全文 Read(差分レビュー)— API整合(engine.tell の形式等)を目視
  3. SMOKE実行 → 出力とCSVの両方を確認(値だけでなく**ファイル名・列も**見る)
  4. 合格後に本走投入。不合格は自分で修正(terraに差し戻すより速い)

#### sol への理論・数値レビュー委譲

- **何を**: 数学的正しさの監査(論文パラメータ・数式・決定性)、候補リストの吟味、
  ドキュメント整合性チェック
- **どこまで**: 指摘リストの生成まで。**ファイル変更はさせない**(read-only、`-s`なし)
- **プロンプト必須要素**: (1)diffまたは対象ファイルの絶対パス (2)監査観点の列挙
  (a,b,c...と番号付け — 観点を書かないと一般論が返る) (3)「結論は問題点リスト+重大度」
  (4)当プロジェクト固有の前提(GPでなくMLPアンサンブル、決定性が仕様、棄却済みリスト)
- **後処理**: 指摘を1件ずつ採否判断(全採用が正解とは限らない — 「同じ問題」表現の
  精緻化のように部分採用もある)→ 反映 → 再ビルド+ビット一致で回帰確認

#### sol ultra(xhigh)への最終監査委譲

- **何を**: A/B採否・公開物に直結する最終実装のみ(日常レビューに使わない)
- **タイミング**: **A/Bベンチ投入の前**(順序を誤ると欠陥版の測定結果を破棄する羽目に
  なる — raasp75の128ラン破棄が実例)
- **出力の受け方**: `> file 2>&1` で全量リダイレクトし Read で読む
  (`| tail -N` は前半を失う — 再監査48kトークンの実例)
- **後処理**: [高]指摘は必ず修正+該当A/Bの再測定。[低]は採否をコメントつきで記録

#### サブエージェント(Explore)へのコード・文書調査委譲

- **何を**: 10ファイル級の横断読み取り(陳腐化監査、実装箇所の行番号特定)
- **プロンプト必須要素**: 対象ファイルの列挙+観点の番号付け+「行番号つきで」+語数上限
- **後処理**: **報告された数値(行数・テスト数)は必ず実測で裏取り**してから文書に書く
  (今回は全一致だったが、裏取りは固定費として払う)

#### サブエージェント(general-purpose)への文献調査委譲

- **何を**: Web文献調査。**直交する軸で3体に分割**(今回: MF-BO/高次元/サロゲート —
  重複ほぼゼロで機能)。同一テーマの競争起用はコスト2倍に見合わず不採用
- **プロンプト必須要素**: (1)エンジン構成の明示(「GPではなくMLPアンサンブル」)
  (2)**棄却済み案リストの貼り付け(全員に)** — 1体への渡し忘れが再提案を招いた
  (3)定量値必須 (4)適合性・実装コスト・リスクの評価軸 (5)成果物の語数上限
- **後処理**: 統合は指揮官が行う(調査者に選定させない)。統合時に棄却済み・重複を
  濾過 → 統合リストを sol の吟味へ回す(調査→吟味→実装の三段分離)

### 6.2 特筆すべき運用パターン(再現価値が高いもの)

1. **「調査 → 吟味 → 実装 → 監査 → 実測」の五段パイプライン**: 各段の担い手を変える
   (サブエージェント→sol→Claude/terra→sol ultra→ベンチ)。/goalジョブでは
   これで見送り5件を実装前に落とし、実装後の欠陥1件をA/B判定前に捕まえた
2. **欠陥検出時のデータ規律**: 監査で欠陥が出たら、欠陥版で収集済みのA/B行を
   CSVから`grep -v`で削除 → bench_resumeが該当分だけ再実行。判定は常に修正版の
   データで行う(手順: CSV行削除→再ビルド→同じコマンドで再起動、で完結する設計に
   ハーネスを作っておくことが前提)
3. **委譲と自前の即時切替**: terraハング(無出力1.5h)を検知したら kill して自前実装へ。
   「委譲のリトライ」より「自前への切替」が速いのはスクリプト級まで
4. **並列化の骨格**: 長時間ベンチ(nohup+ログ)を先に着火 → 待ち時間に調査委譲・
   実装・レビューを重ねる。ScheduleWakeup/バックグラウンド通知で回収
5. **指揮官が絶対に手放さないもの**: コアアルゴリズム変更、ビット一致検証の実行、
   A/B採否判定、コミット、ユーザーへの数値報告。ここを委譲しない限り、
   どの委譲先が壊れても損害は「時間」で済み「正しさ」には及ばない


## Codex内蔵マルチエージェント運用(2026-07-12以降)

Codexのみで作業するセッションでは、上記Codex CLI役割を内蔵サブエージェントへ置換する。
rootが設計・コア実装・統合・採否を保持し、読み取り調査と独立監査だけをサブエージェントへ委譲する。

- 調査: 直交する最大3タスクへ分割し、全員へ棄却済みリストを渡す。出力は結論と根拠に限定する。
- 生存確認: 委譲先は4分以内ごとに完了項目・次作業・変更ファイル・阻害要因を通知する。rootは待機中60秒ごとに状態を確認し、5分無通信で確認要求、さらに60秒無応答なら中断して回収する。
- 実装: Rustコアと小変更はrootが担当する。定型ハーネスのみ委譲可能だが、rootが全文差分・テスト・SMOKEを検収する。
- 監査: 実装担当と異なる読み取り専用エージェントが、決定性・状態往復・数値式・試験設計を確認する。監査合格前にA/Bを起動しない。
- 実測: 単体試験→フラグOFFビット一致→SMOKE→本走。相関等の事前ゲートを通らない高コスト本走は省略する。
